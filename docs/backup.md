# Backup & Reliability

## Overview

KraKeN Infrastructure uses a layered backup strategy designed to provide both fast local recovery and off-site disaster recovery.

The backup architecture separates infrastructure configuration, persistent application data, secrets, and transient runtime data.

The primary objectives are:

* Protect critical infrastructure configuration
* Preserve persistent application and monitoring data
* Provide fast local recovery
* Provide off-site disaster recovery
* Prevent secrets from being committed to source control
* Verify backups before removing older backup sets
* Maintain a tested restore procedure

---

## Backup Architecture

```text
                         KraKeN VPS
                             │
                             │
                    Backup / Encryption
                             │
              ┌──────────────┴──────────────┐
              │                             │
              ▼                             ▼
      Local Backup Store              Cloudflare R2
      /opt/kraken/backups/            Private Bucket
              │                             │
        Fast Recovery                Disaster Recovery
```

### Recovery Layers

| Layer             | Purpose                                                 |
| ----------------- | ------------------------------------------------------- |
| GitHub            | Source of truth for reproducible code and configuration |
| Local backup      | Fast recovery from accidental changes or data loss      |
| Cloudflare R2     | Off-site disaster recovery                              |
| Encrypted secrets | Protection of sensitive credentials and keys            |

## Backup Scope

### Infrastructure Configuration

The following directories are included in the backup scope:

```text
/opt/kraken/compose/
/opt/kraken/config/
/opt/kraken/scripts/
/opt/kraken/systemd/
```

These contain infrastructure configuration, service definitions, automation scripts, and deployment-related configuration.

### Persistent Data

The following persistent data is included:

```text
/opt/kraken/data/grafana/
/opt/kraken/data/prometheus/
/opt/kraken/data/node-exporter/
```

Grafana data is considered important because it contains persistent Grafana state such as dashboards and configuration.

Prometheus data is backed up to preserve historical monitoring data. Loss of Prometheus history does not prevent the monitoring stack from being rebuilt, but retaining the data improves recovery capability.

Node Exporter textfile data is included because it contains custom infrastructure metrics generated by KraKeN automation.

---

## Excluded Data

The following data is excluded from normal backup archives:

```text
/opt/kraken/backups/
```

The backup destination must not recursively back up itself.

Transient Prometheus runtime files are also excluded where appropriate, including:

```text
lock
queries.active
```

Other temporary files, runtime state, Docker image caches, stopped containers, and container runtime metadata are not considered part of the infrastructure backup.

Docker named volumes are currently not present on the VPS. Persistent application data currently uses bind mounts under `/opt/kraken/data/`.

---

## Secrets Strategy

Secrets are handled separately from the normal infrastructure archive.

Sensitive files may include:

```text
/opt/kraken/compose/.env
/opt/kraken/secrets/
```

Secrets must:

* Never be committed to GitHub
* Never be included in plaintext public repositories
* Never be exposed through public URLs
* Be stored with restrictive filesystem permissions
* Be encrypted when included in disaster-recovery backups

The repository provides configuration templates such as `.env.example` rather than real credentials.

---

## Backup Destinations

### Local Backup

Local backups are stored under:

```text
/opt/kraken/backups/
```

The local backup store is intended for fast recovery from:

* Accidental configuration changes
* Failed deployments
* Corrupted application data
* Recent operational mistakes

Local backups are not considered sufficient for disaster recovery because they reside on the same VPS.

### Cloudflare R2

Cloudflare R2 is the off-site disaster-recovery destination.

The R2 bucket will remain private and will use a bucket-scoped API credential with only the permissions required for backup operations.

Planned permission scope:

```text
Object Read & Write
```

The credential will be restricted to the dedicated KraKeN backup bucket.

R2 credentials will be stored outside GitHub and handled as secrets on the VPS.

---

## Retention Policy

The initial retention policy is:

| Backup Type | Retention |
| ----------- | --------: |
| Daily       |         7 |
| Weekly      |         4 |
| Monthly     |         3 |

The same logical retention policy applies to both local backups and the R2 disaster-recovery repository.

The retention process must only remove older backups after the newest backup has been successfully:

1. Created
2. Verified
3. Stored locally
4. Uploaded to R2
5. Verified remotely

A failed backup operation must not trigger destructive retention cleanup.

---

## Archive Format

Backups will use compressed archives:

```text
tar + zstd
```

The resulting backup will then be encrypted before being stored as a disaster-recovery backup.

Planned filename format:

```text
kraken-backup-YYYY-MM-DD_HHMMSS.tar.zst.enc
```

Example:

```text
kraken-backup-2026-09-29_013000.tar.zst.enc
```

Associated verification files:

```text
kraken-backup-YYYY-MM-DD_HHMMSS.sha256
kraken-backup-YYYY-MM-DD_HHMMSS.manifest
```

The manifest records the backup contents and provides an additional reference during restore operations.

## Backup Flow

The backup process is designed around the following sequence:

```text
Validate Environment
        │
        ▼
Create Backup Timestamp
        │
        ▼
Collect Backup Scope
        │
        ▼
Exclude Runtime / Temporary Data
        │
        ▼
Create tar + zstd Archive
        │
        ▼
Encrypt Backup
        │
        ▼
Generate SHA-256 Checksum
        │
        ▼
Generate Manifest
        │
        ▼
Verify Backup
        │
        ▼
Store Local Backup
        │
        ▼
Upload to Cloudflare R2
        │
        ▼
Verify R2 Object
        │
        ▼
Apply Retention Policy
```

Retention cleanup must occur only after successful backup and verification.

---

## Integrity Verification

Each backup must have integrity information associated with it.

SHA-256 checksums will be used to detect:

* Corrupted backup files
* Incomplete transfers
* Unexpected modifications

Example:

```text
backup archive
      │
      ▼
SHA-256 checksum
      │
      ▼
stored with backup metadata
```

The restore process must verify the checksum before attempting extraction.

---

## Failure Handling

The backup process must fail safely.

Examples of failure conditions include:

* Insufficient disk space
* Archive creation failure
* Encryption failure
* Checksum generation failure
* Invalid backup contents
* R2 authentication failure
* R2 upload failure
* R2 verification failure

When a failure occurs:

* The script must return a non-zero exit status
* The failed backup must not be treated as valid
* Existing valid backups must not be deleted
* Retention cleanup must not proceed
* The failure should be logged for troubleshooting

---

## Restore Strategy

Restore procedures will be documented after the backup implementation is completed.

The intended recovery workflow is:

```text
Select Known-Good Backup
        │
        ▼
Verify Checksum
        │
        ▼
Decrypt Backup
        │
        ▼
Extract Backup
        │
        ▼
Restore Configuration
        │
        ▼
Restore Persistent Data
        │
        ▼
Restart Services
        │
        ▼
Verify Infrastructure
```

A backup will not be considered fully reliable until an actual restore test has been completed.

---

## Recovery Testing

The final Phase 4 validation will include a controlled recovery test.

The test will verify that the backup can be used to restore:

* Docker Compose configuration
* Prometheus configuration
* Grafana state
* Custom monitoring scripts
* Systemd automation
* Persistent monitoring data where applicable

The recovery test will be performed without relying on the original backup source being intact.

## Design Principles

The KraKeN backup system follows these principles:

1. **Backups must be restorable, not merely created.**
2. **Local storage provides fast recovery but is not sufficient for disaster recovery.**
3. **Off-site backups must be stored separately from the VPS.**
4. **Secrets must never enter source control.**
5. **Sensitive disaster-recovery data must be encrypted.**
6. **Backup verification must occur before retention cleanup.**
7. **Failed backups must never trigger destructive cleanup.**
8. **GitHub remains the source of truth for reproducible infrastructure code and configuration.**
9. **Backup architecture should remain reproducible and automation-friendly.**
10. **Recovery procedures must be tested before the backup system is considered complete.**
